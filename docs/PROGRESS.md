## 現在のブロッカー / 要判断

1. **残る精度不足への 3 段構え（Phase 8・8a 実機確認済 / 8b 実機計測済 / 8c 着手中）**: Phase 7 の TSDF 化後もユーザ所感は「今ひとつ精度がよくない」。原因を 2 つに分けて潰す。
   - **8a 深度品質フィルタ（実装済・実機未確認）**: 物体の輪郭で生じる **flying pixel**（前景と背景を平均した画素が宙に浮く＝「缶が縦に尾を引く」の正体）を棄却し、浅い角度（grazing）の観測は重みを下げる。隣接テクセルの深度勾配から面の傾き `tanθ` を 1 つ求め、大きすぎれば段差として棄却・中程度なら `cosθ` を重みに掛ける。センサのジッタを傾きと誤認しないようデッドバンド付き。
   - **8b 信頼度の確定・ロック・半透明（未着手）**: セルごとに「最短観測距離」と「観測方向の多様性」を持ち、基準を満たしたら**確定**＝不透明で描画し、**遠くからの観測では変更も削除もされない**。未確定は**半透明**で描き「近づけ」と伝える。ユーザ合意: 確定後も**近づけば再修正可**／2 段階の半透明／確定しきい値はスライダー。
   - 設計と根拠は `docs/RESEARCH.md` の追加調査（KinectFusion / voxblox / RTAB-Map）を参照。
2. ~~**遠距離の観測が近距離スキャンを劣化させる（Phase 6.5）**~~ → TSDF の重み設計に統合（下記は経緯として保存）: ユーザ指摘「近くでスキャンして精度が上がっても、遠くから同じ場所が写り込むとまた精度が落ちるのでは？」→ **その通りだった**。3 経路すべてで劣化していた: (a) 色は 1/d 重みでも遠距離観測が**累積し続ける**ので近距離の色を薄める、(b) 占有は距離無関係に +1 で、遠距離ノイズが**きれいな面の周りに誤セルを作る**、(c) カービングは遠距離の誤差の大きい深度が「面より奥」と読むと**正しい面を削る**。マップ作成用途なのに品質が単調改善しない設計の穴。→ **セルごとに `bestDist`（最も近くから観測した距離）を記憶し、非対称ルール**を導入: **より近い観測は追加・更新・カービングすべて可**、**`qualityRatio`(1.5) 倍より遠い観測はそのセルに一切触れない**。これで一度近くで撮った所は後から遠くに写り込んでも劣化せず、品質は上がる一方になる。残る限界: 遠距離観測が**未観測の場所に新しい誤セルを作る**ことは防げない（ただし近づけばカービングで消える＝自己修復）。
3. **占有値の無制限増加＝カービング/しきい値が無効化していた（Phase 6.4 で修正・実機確認済）**: Phase 6.3 のスライダーが「変えても分からない」と報告され、原因を数値で特定 —
   - 深度は毎フレーム **3,600 点**（160×90 / stride 2）。1 か所を見続けると 1 セルが **毎秒 +30〜60**、数秒で `count` が数百に育つ。**ノイズも同様に育つ**ため、`minObs` 3 でも 14 でも一瞬で超え、**しきい値として機能していなかった**（＝スライダーが効かない）。
   - カービングの減算は「毎フレーム `CARVE_BUDGET` 個ずつ検査」＝ 25 万描画で **1 周 0.5〜1 秒 → 毎秒 −2 程度**。加算 +30〜60/秒 に対して桁違いに弱く、しかも count が数百まで育っているため **消えるのに数分**かかっていた（＝「一応消える」が「また出る」）。
   - → **占有値に上限 `OCC_MAX`(10) を設定**（色の平均は従来どおり無制限に精緻化）。加算は 10 で頭打ち、カービングは `CARVE_MISS`(2)/回、`CARVE_BUDGET` を 16,000 に増やし、**約 1〜2 秒で消える**ように。`minObs` は「今どれだけ強く支持されているか」を表す実効的な値になり、スライダー(1〜8)が意味を持つ。
4. **カービング（Phase 6.2）**: 浮きは消えるが遅すぎた → 6.4 で実効化（実機確認済）。**既知の限界**: 俯瞰プレビューは削除を反映しない(暫定)。2cm ライブ色は最初の色で固定。
5. **超広域の範囲（Phase 6.1 で 200 万まで拡大済み・実機で 966k まで確認）**: さらに広い場が必要なら SoA 化(省メモリ)か走査解像度可変を検討。
6. **キャッシュ対策**: 画面に `build:` 時刻を表示。古い版を見てしまったら `?v=<番号>` を付けて開くと最新が読める（GitHub Pages は index.html を ~10分キャッシュするため）。

## Phase 8b 実機計測（2026-07-26 / FPS の原因特定）

確定/暫定の分類は動作を確認（147,848 / 119,990 など）。あわせて追加した計測行が FPS 低下の原因を確定させた。

| 指標          | 計測 A            | 計測 B          |
| ------------- | ----------------- | --------------- |
| FPS           | 18（55.6ms/frame) | 8（125ms/frame) |
| TSDF セル     | 1,389,901         | 899,132         |
| 描画中        | 267,838           | 210,020         |
| **CPU ms 計** | **52.7**          | **89.3**        |
| ├ 描画(gl)    | 0.4               | 3.7             |
| ├ **融合**    | **19.3**          | **27.5**        |
| ├ 追記        | 6.6               | 8.9             |
| ├ **除去**    | **19.8**          | **33.7**        |
| └ 俯瞰        | 6.6               | 15.5            |
| JS ヒープ     | 321 / 1856 MB     | 357 / 1856 MB   |

**結論**:

- **CPU 律速**。CPU 計 52.7ms がフレーム 55.6ms の **95%** を占める。
- **GPU ではない**。`描画`(renderer.render の CPU 側)は 0.4〜3.7ms。26 万インスタンスでも描画発行は安い。
- **メモリでもない**。321〜357MB / 上限 1856MB。実機のセルあたりは約 231B で、事前のデスクトップ合成ベンチ 383B/766MB は**保持されたままの dirty セットによる過大評価**だった。→ SoA 化の動機は「メモリ削減」ではなく**速度**に変わった。
- 犯人は **`融合` + `除去` で約 7 割**。どちらも **140 万件の `Map` 参照**が支配的（除去は 16,000 件/frame で 1 件あたり約 1.24µs、readVoxel 単体でほぼ説明がつく）。
- キーは最大 2.25e15 で **V8 の小整数(SMI)範囲外** → 全キーがボックス化 double。合成ベンチ（140 万件・16,000 回参照）で **2e15 キー 9.07ms → 2^30 未満キー 4.88ms（1.9 倍速）**。

**第 1 弾（本コミット）— 冗長処理の除去**（いずれも挙動不変）:

- `readVoxel` の `unpackKey` をインライン化。毎回 `{xi,yi,zi}` を確保していた（carve だけで 16,000 個/frame の生ゴミ）
- `carve` が `readVoxel` の出した座標を捨てて**キーを二度 unpack**していたのを解消（合成ベンチで 0.62ms/frame 相当）
- 融合の帯は表示帯より広く、**面帯の外のセルは描画側もプレビュー側も即捨てていた** → dirty マークを面帯内に限定（帯 4 セル中およそ 3 セル分の削減）
- 俯瞰プレビューが pending を**二周**して `readVoxel` していたのを一周に

> 第 1 弾だけでは 18fps→60fps には届かない見込み（除去の約 8% 相当）。本命は格納の型付き配列化。

### 第 2 弾 — 格納を型付き配列の開番地ハッシュ表へ

`Map<number, {…}>` を捨て、**Float32Array 1 本**の開番地ハッシュ表（線形探索）に置き換えた。キーは整数セル座標 3 つを直接ハッシュするので、2.25e15 のパックキーをボックス化 double として扱う必要がなくなる。

**フィールドはインターリーブ**（1 スロット = 連続 48 バイト）。ここは実測で決めた: 1 フィールド 1 配列の「並列配列」にすると**参照は 2.8 倍速くなる一方、融合が 1.8 倍遅くなった** — 融合は 1 セルの 8 フィールドを読み書きするので、フィールドごとに配列を分けると 1 セルあたり 8 本のキャッシュラインを触ることになるため。インターリーブなら両方の使い方で 1〜2 ライン。

Float64 も試したが差はなかった（融合 7.83 対 7.84）ので Float32 のまま。

合成ベンチ（107 万セルの部屋・ウォームアップ後の定常状態）:

| 指標                         | Map     | 型付き配列  |              |
| ---------------------------- | ------- | ----------- | ------------ |
| 参照 16,000 回 (`readVoxel`) | 8.21 ms | **1.96 ms** | **4.2 倍速** |
| 融合 (定常)                  | 5.21 ms | 5.37 ms     | 同等         |
| ヒープ                       | 409 MB  | **169 MB**  | **2.4 倍減** |

> 当初「融合が 1.3 倍遅い」と出たのは、計測窓の中でテーブル再ハッシュが 1 回起きていたため。ウォームアップを入れると同等になる。再ハッシュは 1 セッションに数回しか起きない。

実機フレームへの外挿: `除去` 19.8→約 4.7ms、`追記` 6.6→約 1.6ms、`俯瞰` 6.6→約 2.5ms、`融合` は据え置き 19.3ms → **CPU 計 52.7→約 29ms、FPS 18→30 前後**の見込み。以降は `融合` が最大項目になる。
