## 2026-07-26 — Phase 8c: FPS の原因特定と、セル格納の型付き配列化

### なぜ

Phase 8b で HUD に入れた CPU 段別計測が、FPS 低下の原因を確定させた。**推測していた 2 つの候補は両方とも外れ**だった。

| 指標          | 計測 A            | 計測 B          |
| ------------- | ----------------- | --------------- |
| FPS           | 18（55.6ms/frame) | 8（125ms/frame) |
| **CPU ms 計** | **52.7**          | **89.3**        |
| ├ 描画(gl)    | 0.4               | 3.7             |
| ├ **融合**    | **19.3**          | **27.5**        |
| ├ 追記        | 6.6               | 8.9             |
| ├ **除去**    | **19.8**          | **33.7**        |
| └ 俯瞰        | 6.6               | 15.5            |
| JS ヒープ     | 321 / 1856 MB     | 357 / 1856 MB   |

- **CPU 律速**。52.7ms がフレーム 55.6ms の 95%。
- **GPU ではない**。`描画` は 26 万インスタンスでも 0.4〜3.7ms。「表示サイズを上げれば戻るはず」という当初の見立ては誤り。
- **メモリでもない**。321MB / 上限 1856MB。事前のデスクトップ合成ベンチ「383B/セル・766MB」は**保持されたままの dirty セットによる過大評価**だった（実機は約 231B/セル）。→ SoA 化の動機は「メモリ削減」ではなく**速度**に変わった。
- 犯人は `融合` + `除去` で約 7 割。どちらも **140 万件の `Map` 参照**が支配的。パックキーは最大 2.25e15 で **V8 の小整数(SMI)域外**なので、全キーがボックス化された heap number になっていた。

合成ベンチ（140 万件・16,000 回参照）: **2e15 キー 9.07ms 対 2^30 未満キー 4.88ms**。

### 何を

**第 1 弾 — 冗長処理の除去**（挙動不変）:

- `readVoxel` の `unpackKey` をインライン化。毎回 `{xi,yi,zi}` を確保していた（carve だけで 16,000 個/frame）
- `carve` が `readVoxel` の出した座標を捨てて**キーを二度 unpack**していたのを解消
- 融合の帯は表示帯より広く、**面帯の外のセルは描画側もプレビュー側も即捨てて**いたので、dirty マークを面帯内に限定（帯 4 セル中およそ 3 セル分の削減）
- 俯瞰プレビューの pending 二周読みを一周に

**第 2 弾 — 格納を型付き配列 1 本の開番地ハッシュ表へ**:

`Map<number, {…}>` を捨て、**Float32Array 1 本**の開番地ハッシュ表（線形探索・トゥームストーン削除・負荷率 0.7 で再ハッシュ）に置き換えた。キーは整数セル座標 3 つを `Math.imul` で直接ハッシュするので、巨大なパックキーをボックス化する必要がなくなる。パックキー自体は**外部ハンドルとして据え置き**（描画側のインスタンス表や dirty セットが持っているため。再ハッシュでスロットは動くがキーは動かない）。

**フィールドはインターリーブ**（1 スロット = 連続 48 バイト）。これは実測で決めた: 1 フィールド 1 配列の並列配列にすると**参照は 2.8 倍速くなる一方、融合が 1.8 倍遅くなった** — 融合は 1 セルの 8 フィールドを読み書きするので、分けると 1 セルあたり 8 本のキャッシュラインを触ることになる。インターリーブなら両方の使い方で 1〜2 ライン。Float64 も試したが差はなかった（融合 7.83 対 7.84）ので Float32 のまま。

| 合成ベンチ（107 万セル・定常） | Map     | 型付き配列  |              |
| ------------------------------ | ------- | ----------- | ------------ |
| 参照 16,000 回                 | 8.21 ms | **1.96 ms** | **4.2 倍速** |
| 融合                           | 5.21 ms | 5.37 ms     | 同等         |
| ヒープ                         | 409 MB  | **169 MB**  | **2.4 倍減** |

当初「融合が 1.3 倍遅い」と出たのは**計測窓の中でテーブル再ハッシュが 1 回起きていた**ため。ウォームアップを入れると同等になる。再ハッシュは 1 セッションに数回しか起きない。

### 検証

- 型/テスト **126**（+10）/ ビルド green。**公開 API は不変**なので既存テストは無改変で通過
- ハッシュ表そのものの危ない部分を追加でテスト: 複数回の再ハッシュを跨いで全セルが正しく引けること、座標の並べ替え（(1,2,3) と (3,2,1)）が衝突しないこと、**削除したセルの先にあるセルが引けること**（トゥームストーンが無いと探索が途中で止まる）、削除スロットの再利用でサイズが漏れないこと、消したセルを測り直すと**古い値の復活ではなく新規セル**になること、`maxVoxels` 到達後も既存セルは更新できること、キー範囲外の拒否、`clear` 後の再利用
- テスト作成中に `i * 0.02` がセル境界に乗って浮動小数の丸めで隣のセルに入る問題を踏んだ（3 × 0.02 / 0.02 = 2.9999999999999996）。セル中心で指定するよう修正

### なぜ

Phase 7（TSDF 化）と 8a（深度品質フィルタ）を経ても所感は「今ひとつ精度がよくない」。ユーザ要望は 3 点:

1. 精度よく読み取る
2. **精度がよいボクセルは固定**して、離れても消えないようにする
3. **精度の良くないボクセルは半透明**で表現し、「近づく必要がある」と分かるようにする

TSDF の「重み」だけでは (2)(3) を表現できない。重みは**何回観測したか**しか表さず、「部屋の反対側から 10 秒眺めた」と「真横まで歩み寄った」を区別しない。深度誤差は距離とともに急激に増えるので、信頼度を決めるのは**回数ではなく近さ**である。

### 何を

**1. セルごとの信頼度（`src/voxel/grid.ts`）**

`VoxelRecord` に 2 つ追加:

| フィールド  | 意味                                      | 更新  |
| ----------- | ----------------------------------------- | ----- |
| `bestDepth` | そのセルを**最も近くから見た距離**(m)     | `min` |
| `dirMask`   | **観測方向**の水平 8 セクタのビットマスク | `OR`  |

`min` と `OR` はどちらも**冪等**なので、`fuse.ts` が 1 測定につき帯に沿って `integrate` を約 4 回呼ぶ現状でも**二重計上が原理的に起きない**（カウンタ方式なら必要だった重複排除が不要）。方向ビットは `azimuthBit(dx, dz)` として測定ごとに 1 回だけ計算する。

**2. 確定の判定**

```
w >= confirmWeight かつ (bestDepth <= confirmDist または 方向数 >= confirmDirs)
```

距離と方向の **OR** が要点。**平らな壁は片側からしか見られない**ので、方向の多様性を必須にすると壁が永久に確定しない。逆に、ぐるりと回り込んだ物体は多少遠くても十分に拘束されている。

**3. ロック（確定セルの保護）**

`integrate` と `integrateFree` の**両方**で、確定済みセルは `bestDepth × lockRatio`(既定 2) より遠い観測を**拒否**する。遠方からの観測は融合もカービングもできない＝**離れても消えない**。近づけば再び上書きできるので、誤った形が確定しても修正可能。

**4. カービング重みの是正（`src/xr/carve.ts`）**

調査中に見つけた実際のバグ。融合は `quality/d²` で重み付けしていたのに、カービングは**距離に関係なく固定重み 2** だった。3m から見ると融合は 0.11、カービングは 2 — つまり**遠距離では消す力が加える力の約 18 倍**。「近くでスキャンして精度が上がっても、遠くから写り込むとまた精度が落ちる」という報告の直接の原因がこれ。`carveWeightScale(d) = 1/d²` を掛けて融合と同じ減衰に揃えた。

**5. 2 レイヤ描画（`src/render/voxelRenderer.ts`）**

three.js r185 の `instanceColor` は **RGB のみ**（itemSize 3 固定）で per-instance の不透明度が存在しないため、シェーダ改造ではなく **2 つの `InstancedMesh`**（確定=不透明 / 暫定=`transparent, opacity 0.35, depthWrite false`）を使う。単一メッシュのロジック（特に繊細な swap-remove の索引管理）を内部クラス `VoxelLayer` に切り出して**そのまま 2 回インスタンス化**した。両者は `Group` にまとめてあるので `scene.add(voxels.root)` の 1 行のまま。

`applyUpdates` は追記専用で描画済みインスタンスを二度と見ないため、**確定への昇格は `carve` の巡回**（毎フレーム 16,000 個のローリング）で検出してレイヤ間を移動させる。

**6. 俯瞰プレビュー**

`putImageData` は**置換**なので alpha を下げると canvas 自体が透けてしまう。暫定セルは背景色へブレンド（`blendToBackground`）して、3D と同じ「まだ確定していない」印象を出す。

### FPS 15 の発見と計測の導入

実機スクリーンショットで **FPS 15〜16** を確認した（Phase 4 の実測は描画 15 万で FPS 74）。セル数 163 万でも 30 万でも 15〜16 だったので、セル数だけでは説明できない。合成ベンチ（デスクトップ・107 万セル）では:

- **383 B/セル → 411 MB**。`GRID_CAP` 200 万なら **約 766 MB**
- 融合 **11.3 ms/frame**、carve 相当の `readVoxel` × 16,000 が **4.0 ms/frame**

原因を推測で潰すのは避け、HUD に **CPU 段別 ms**（`StageTimer`）と **JS ヒープ**を追加した。CPU 段の合計が 1 フレーム時間に近ければ CPU 律速でその内訳が犯人、大きく下回るなら GPU 律速（インスタンス数・塗り面積）と切り分けられる。対策は Phase 8c（SoA 化など）で、実機の数値を見てから。

### 検証

- 型/テスト **112**（+31）/ ビルド green
- 新規テスト: `azimuthBit`/`popcount8`、`bestDepth` の min・`dirMask` の OR、**壁が 1 方向でも距離で確定する**こと、遠い観測が確定セルを**変更も削除もできない**こと、近づけばできること、`carveWeightScale` の距離減衰、`blendToBackground`、`StageTimer` の按分
- `fuse.test.ts` では確定条件を距離のみ／方向のみに切り分けて、帯の 4 回呼び出しでも `bestDepth` が測定距離そのもの（1m の倍数でない）に、方向数が 1 のままになることを確認

## 2026-07-24 — Phase 8a: 深度品質フィルタ（flying pixel 棄却＋浅い角度の重み下げ）

### きっかけ

Phase 7 の TSDF 化後も実機所感は「今ひとつ精度がよくない」。あわせてユーザから「**精度の良いボクセルは固定して離れても消えないように／良くないものは半透明で近づけと分かるように**」という要望。これを 2 段構えに分けた:

- **8a（本エントリ）**: 誤差源そのものを減らす。`docs/RESEARCH.md` の追加調査で未採用だった 2 技術を投入。
- **8b（次）**: 信頼度で確定・ロックし、未確定を半透明で見せる。

分割したのは、どちらが効いたかを切り分けられるようにするため（ユーザ合意）。

### 何を

- `src/xr/reproject.ts`: 隣接テクセルの深度勾配から**面の傾き** `tanθ` を 1 つ復元し、2 つの目的に使う純関数を追加（`carve.ts` の `isFreeSpace` と同じく単体テスト可能な形で export）:
  - `slantTangent(d, dRight, dDown, lateralX, lateralY, stride, noise)` — 2 軸を**直交合成**（＝勾配の大きさ）。
  - `isDepthEdge(slant, threshold)` — 大きすぎる傾きは面ではなく**段差** ＝ flying pixel → 棄却。
  - `qualityFromSlant(slant, minQuality)` — `cosθ` を重み係数に（voxblox の anti-grazing）。下限付き。
  - 走査ループの範囲チェック直後（行列計算の**前**）で判定するので、棄却したサンプルはコストがゼロどころか節約になる。
- `PointSink` に 7 番目の引数 `quality` を追加。`main.ts` の重みが `quality / d²` になり、`fuse.ts` が色の重みを `weight` から導いているので**色にも自動で反映**される。
- `ReprojectStats`（呼び出し側が使い回すオブジェクト）で棄却数を報告し、HUD に `エッジ除去 N / M` を表示。
- 定数: `EDGE_SLANT`(8 ≒ 83°)、`minQuality`(0.1)、ノイズのデッドバンド `0.003m + 1%·d`。

### 主要な判断とその理由

1. **1 つの `tanθ` で「棄却」と「重み下げ」を兼ねる**
   - 理由: flying pixel と grazing は連続した同じ現象（勾配が急なほど怪しい）。別々のしきい値を持つより、1 つの量の大小で扱う方が調整点が減り、意味も明快。
2. **横方向の広がりは FOV を仮定せず毎フレーム実測**
   - 理由: 画像中心の隣接テクセルを既存の逆投影で 2 点飛ばし、その差分を取る。**しかも 2D の長さで測る** — この端末は深度バッファ（160×90 横長）とビュー（縦持ち）が回転しており、片方の成分だけを見るとゼロになってフィルタが黙って無効化される。実際、最初の実装はこの罠に嵌まっていた。
3. **隣接が 0（未計測）なら判定をスキップし、棄却はしない**
   - 理由: 0 は「範囲外」と「未計測」の両方の番兵。棄却扱いにすると**穴という穴が縁から削れていく**。この扱いのおかげで既存の 4 テストも無改変で通る。
4. **列の範囲チェックを明示的に行う**
   - 理由: `data[col + stride + row*W]` は `col+stride >= W` のとき**次の行の先頭**を読んでしまい、右端の列すべてに架空のエッジを作る。最も嵌まりやすい罠なので明示的に弾く。
5. **ノイズのデッドバンド**
   - 理由: これが無いと、0.5m で ±5mm のジッタが `tanθ≈0.5 → 重み 0.89` となり、**このフィルタが最も優遇したいはずの「近くから正対して撮った測定」を逆に減点**してしまう。

### 検証

- ローカル: `tsc --noEmit` green、Vitest **81** green（純関数 13 件＋統合 3 件を追加）、`vite build` 成功。
- 合成ベンチ（160×90/stride3、物体シルエットを含む部屋想定）: **0.3ms/frame**、棄却率 **2.9%**。
- 統合テストで、16×16 の段差フレームに対し**段差に跨る 16 テクセルだけが棄却され、平坦な 240 テクセルは残る**ことを確認。
- 未確認（実機）: 輪郭の尾引きが減るか、`エッジ除去` の実測割合、`FPS`。→ `docs/PROGRESS.md` の Phase 8a 手順で依頼。

## 2026-07-24 — Phase 7: TSDF フュージョンへ方式刷新（占有カウントを廃止）

### きっかけ

Phase 6.5 まで対症療法を重ねても、実機では「机の面が厚い帯になる」「缶が縦に尾を引く」が残った。ユーザから「**同じ思想のアプリで精度のよいものはどうやって実現しているのか調べて反映したい**」との依頼。一次情報を調査した結果、**我々の占有カウント方式が原理的に不利**と判明した（調査詳細は `docs/RESEARCH.md` の追加調査節）。

### 調査の結論

高精度スキャンの標準は **TSDF（切断符号付き距離場）フュージョン**（KinectFusion 2011 →Open3D / voxblox）。各セルに「最寄り面までの**符号付き距離**」と「**重み**」を持ち、加重移動平均で更新する:

```
TSDF  = clamp(SDF / truncDist, -1, +1)
value = (W·value_old + w·TSDF) / (W + w)
W     = min(W + w, maxWeight)
```

これで (1) 面は**ゼロ交差＝サブボクセル精度**で収束、(2) 面の手前を通ったレイが正の距離を書くので**空間除去が内在的**、(3) 重みを **1/z²** にして飽和させると**遠距離観測が原理的に軽くなる**（voxblox は「重み関数の選択が精度に強く影響」と明記）。我々が Phase 6.1〜6.5 で場当たり的に足した品質ロック・占有上限・カービング強度は、すべてこの 3 点の劣化版だった。

### 何を（Phase 7）

- `src/voxel/grid.ts`: **全面書き換え**。`VoxelRecord` を `{ sdf, w, r, g, b, cw }` に。`integrate(x,y,z,sdf,weight,color…)` が加重平均で更新（重みは `maxWeight` で飽和）。`integrateFree(key,w)` は「ここは空」を +truncation 方向へ融合し、完全に空になったセルは削除。面の判定は `isSurface = |sdf| ≤ surfaceBand && w ≥ minWeight`。`forEachSurfacePoint` / `countSurface` / `forEachDownsampled` を面ベースに。
- `src/voxel/fuse.ts`（新規）: 1 つの深度測定を**視線方向の帯**へ融合。手前 `+truncation`（自由空間）〜奥 `truncation/2`（内部）を歩き、各サンプルに `sdf = -s` を書く。色は面近傍のみ。奥側を半分にしたのは、そこは交差を定義できれば十分でセル数を食うため。
- `src/render/voxelRenderer.ts`: `carve` を「**描画中インスタンスの検証＋カービング**」に一般化 — 面でなくなったインスタンスも落とす（融合で交差が動くため）。しきい値は累積重み。
- `src/render/overheadPreview.ts` / `src/main.ts`: 面ベースの API へ追従。重みは `1/depth²`、`STRIDE` 2→3（1 点あたり 1 セル→帯 4〜5 セルに増えた分を相殺）。
- テスト: grid を TSDF 用に全面書き直し（切断・straddle 収束・重み飽和・面抽出・自由空間で面から外れる・色の重み平均・粗化）＋ `fuse` 8 件（帯を書く／ゼロ交差が面に来る／手前は正・奥は負／**サブボクセル復元**／高重みが低重みを上書き／色は面近傍のみ）。計 **68**。

### 主要な判断とその理由

1. **占有カウントを捨てて TSDF に全面移行**（部分導入しない）
   - 理由: 両方を併存させると「面はどちらが決めるのか」が二重管理になる。TSDF は占有の上位互換（重みがそのまま確信度）なので、置き換えるのが最も単純。
2. **帯は「レイに沿って歩く」方式**（ボリューム全体を走査しない）
   - 理由: フラスタム内の全ボクセルを射影する方式は広域で破綻する。測定点ごとに数セルだけ書けば O(測定点数) に収まる。デスクトップ実測で ~2.8ms/frame（stride3）。
3. **奥側の帯を半分に**
   - 理由: 負側は交差を定義するのに必要なだけで、深く書くほどセル数（＝メモリと走査コスト）を食う。広域マップ化という目的に直結する。
4. **色は面近傍のサンプルのみ**
   - 理由: 帯の自由空間側に色を書くと、面の手前の空間が着色されてしまう。実際これをテストが検出した（セル生成時に `colorWeight=0` でも色を種として書いていたバグ）。

### 検証

- ローカル: `tsc --noEmit` green、Vitest **68** green、`vite build` 成功。
- 性能: 合成ベンチ（30 万セル既存、160×90/stride3、帯 4〜5 セル）で **~2.8ms/frame（デスクトップ node）**。実機は数倍かかる想定なので `STRIDE` で調整済み。
- 未確認（実機）: 面が 1 層に収束するか、浮きが見るだけで消えるか、`FPS`。→ `docs/PROGRESS.md` の Phase 7 手順で依頼。

### 未採用（次の候補）

## 2026-07-24 — Phase 6.5: 観測品質ロック（遠距離観測が近距離スキャンを壊さないように）（+ Phase 6.4 実機合格）

### Phase 6.4 実機合格

`build: 22:48Z` を Pixel 9a で確認。**ノイズ除去スライダーが明確に効く**: `1/10` → `描画 153,902`、`8/10` → `描画 12,654`。缶やテーブルの形は残り浮きノイズだけが落ちる。セル数も 88〜92 万 → **15 万台**に激減、`FPS 32〜37`。→ 占有上限の導入は正解だった。

### きっかけ（ユーザの鋭い指摘）

「このアプリは現実空間をスキャンしてマップを作りたい。今の仕様では、近くでスキャンして精度が上がっても、**遠くから同じ場所が写り込むとまた精度が落ちる**よね？」→ **そのとおりだった**。3 経路すべてで劣化していた:

1. **色**: 重みは 1/d で近距離有利だが、遠距離観測も `wSum` に**累積し続ける**。長く遠くから見れば近距離の色を薄めていく。
2. **占有**: 距離に関係なく +1。遠距離の誤差でズレた位置に**新しい誤セル**ができ、きれいな面の周りにノイズ殻を作る。
3. **カービング**: 遠距離の深度は誤差が大きく、実際の面より「奥」を返すことがある → **正しくスキャンした面を削ってしまう**。

マップ作成が目的なのに、品質が**単調改善しない**のが設計の穴だった。

### 何を（Phase 6.5）

- `src/xr/reproject.ts`: `PointSink` に **`depth`（実測距離）** を追加。以降、色の重みも品質判定もこの値を使う（`main` 側の毎点 sqrt が不要になり高速化＋カメラ位置追跡も削除）。
- `src/voxel/grid.ts`: `VoxelRecord` に **`bestDist`**（そのセルを最も近くから観測した距離＝データ品質）を追加。`addPoint(..., obsDist)` / `recordMiss(..., obsDist)` に**非対称ルール**を実装:
  - `obsDist > bestDist × qualityRatio`(既定 1.5) → **そのセルには一切触れない**（追加も削除もしない）。`rejectedLowQuality` を計上。
  - `obsDist < bestDist` → `bestDist` を更新（品質は上がる一方）。
  - `forEachDownsampled` の粗セルは構成セルの**最良 `bestDist`** を継承。
- `src/xr/carve.ts`: `lastVoxelDepth`（直近 `testFree` の視点距離）を公開。
- `src/render/voxelRenderer.ts`: carve が `ctx.lastVoxelDepth` を `recordMiss` に渡す。
- `src/main.ts`: `accumulate` が `depth` を受け取り重み＋品質に使用。統計に `低品質を拒否 N 件`。
- テスト: 遠距離観測の拒否 / 近距離での更新と以後のロック / 遠距離はカービングできない / 近距離なら遠距離生成セルを消せる。計 **67**。

### 主要な判断とその理由

1. **「品質」は距離 1 本で表す**
   - 理由: 深度誤差は距離とともに急増するので、距離は入手可能な最良の品質プロキシ。角度や動きブレも要因だが、追加コストゼロで効果が大きい距離を選んだ。
2. **ルールを非対称にする（良い観測は何でもできる／悪い観測は何もできない）**
   - 理由: これが「マップ品質は単調改善」という不変条件を作る。対称に扱う（例: 常に平均する）と、遠距離を長く見るだけで劣化してしまう。近づけば必ず直せる、という体験にもなる。
3. **拒否は「無視」であって「弱く反映」ではない**
   - 理由: 弱く反映しても累積すればいずれ支配する（今回の色の失敗と同じ轍）。有界性を保つには完全に無視するのが確実。
4. **未観測セルは距離に関わらず作る**
   - 理由: 遠方を全く取り込めないと「広いフィールドのマップ化」ができない。遠距離生成セルは `bestDist` が大きい＝低品質と記録されるので、後から近づけば更新も除去もできる（自己修復）。

### 検証

- ローカル: `tsc --noEmit` green、Vitest **67** green、`vite build` 成功。既存 63 件は `obsDist` 既定 `Infinity` により挙動不変。
- 未確認（実機）: 近接スキャン後に遠方から写しても崩れないか、`低品質を拒否` が出るか、遠→近の更新が効くか。→ `docs/PROGRESS.md` の Phase 6.5 手順で依頼。

### 残る限界

遠距離観測が**未観測の場所に**誤セルを作ることは防げない（近づけばカービングで消える＝自己修復）。目立つようなら生成距離の上限導入を検討。

## 2026-07-24 — Phase 6.4: 占有値に上限を設けカービング/しきい値を実効化（Phase 6.3 の設計不備の修正）

### きっかけ（実機フィードバック）

「スキャン安定性って結局どんなパラメータ？変更してもよく分からない」。→ 調べたところ **Phase 6.3 のしきい値は設計上ほぼ無効**だった。私の設計ミスなので数値で明記しておく。

### 原因（数値）

- 深度は毎フレーム **3,600 点**（160×90 / stride 2）。1 か所を見続けると 1 セルは **毎秒 +30〜60**、数秒で `count` が数百に達する。**ノイズセルも同じ速度で育つ**ため、`minObs` が 3 でも 14 でも一瞬で超え、真の面とノイズを区別できていなかった（＝スライダーが効かない）。

### 何を（Phase 6.4）

- `src/voxel/grid.ts`: `maxOccupancy`（既定 10）を追加し、`addPoint` の `count` 加算を **上限で飽和**させる。**色の sum は従来どおり無制限に累積**するので平均色は見続けるほど精緻になる（占有と色の役割を分離）。
- `src/main.ts`: `OCC_MAX`(10) をグリッドに渡す。`CARVE_MISS`(2) を新設し carve に渡す、`CARVE_BUDGET` 8,000→**16,000**。`minObs` の既定を 3、スライダー範囲を **1〜8**（`OCC_MAX` 未満に制限）へ。UI 名称を「スキャン安定性」→ **「ノイズ除去」**、表示を `3 / 10` 形式にして*上限に対する比*であることを明示。
- `src/render/voxelRenderer.ts`: `carve(..., missStrength)` を追加し `recordMiss` に伝播。
- テスト: 占有飽和（500 回ヒットしても 10 / 5 回のカービングで削除）と、飽和後も色平均が更新されること。計 **63**。

### 効果（設計値）

占有 10 上限・カービング −2/周・1 周 ≈0.3 秒（budget 16,000 / 25 万描画）→ **浮きボクセルは約 1〜2 秒で消える**（従来は数分）。`minObs` は「今どれだけ強く支持されているか」を表す実効値になり、スライダーが体感できるはず。

### 学び

**しきい値は、対になる量が有界でなければ機能しない。** 無制限に増える `count` に対する `minObs` は、実質「一度でも見たか」でしかなかった。カウンタを飽和させ、加算と減算のレートを設計して初めて、しきい値もカービングも意味を持つ。

### 検証

- ローカル: `tsc --noEmit` green、Vitest **63** green、`vite build` 成功。
- 未確認（実機）: 浮きが 1〜2 秒で消えるか、ノイズ除去スライダーの差が見えるか、`FPS`。→ `docs/PROGRESS.md` の Phase 6.4 手順で依頼。

## 2026-07-24 — Phase 6.3: スキャン安定性(minObs)スライダーでノイズ低減（+ Phase 6.2 実機確認）

### Phase 6.2 実機確認と本質課題の特定

`build: 02:11Z` を Pixel 9a で確認。カービングで浮きは「一応消える」。だが所感「スキャン精度自体が低く、別角度に動くと中に浮くボクセルが結構出る」。実測 `ボクセル 88〜92 万`・`描画 250,000/250,000`(上限飽和)・`FPS 24〜32`。→ **本質はスキャンノイズ**。低解像度深度(160×90)＋姿勢ドリフトで同じ面が角度ごとに少しずれ、面の周りに厚いノイズ殻ができる。カービング(手前 8cm)は殻を消せない。

### 何を（Phase 6.3）

- `src/main.ts`: `MIN_OBS` 定数(3)を **`state.minObs`(既定 6)** に変更し、`applyUpdates`/`carve`/`overhead.update`/`rebuildDownsampled` へ渡す。HUD に **「スキャン安定性」スライダー**(3〜14)を追加。ドラッグでラベル更新、離すと既存セルを新しきい値で**再構成**(k=1: `reset()`＋`markAllDirty()`、k>1: `rebuildDownsampled`)＝再スキャン不要。統計に `安定性(minObs)` 行。フェーズ表示/説明文を現状(品質調整)に更新。
- しきい値のしくみ: `count`(net 占有)が `minObs` 以上のセルだけ描く。真の面は全角度から観測され `count` 大、ノイズ殻は一部角度のみで `count` 小。→ minObs を上げると殻が落ちて面が残る。

### 主要な判断とその理由

1. **ノイズ低減の主レバーは minObs、かつ固定値でなくスライダーに**
   - 理由: 最適な minObs はシーン/端末依存で、実機トライ＆エラーが要る。スライダーなら実機でライブに最適点を探せ、デプロイ往復を減らせる（表示サイズスライダーと同型）。既定を 3→6 に上げてまず素の状態でノイズを減らす。
2. **変更時は既存データを再構成（再スキャンなし）**
   - 理由: しきい値は「描画に必要な観測数」で、既に蓄積したセルの描画可否だけが変わる。`markAllDirty()`＋差分再追加で、スキャンし直さず即反映できる。
3. **FPS もこれで回復見込み**
   - 理由: 充填 0.9(大きめキューブ)のオーバードローで 250k 描画時に 24〜32fps へ低下していた。minObs↑ で描画数が上限(25 万)未満に減れば、キューブ数が減り FPS が戻る。

### 検証

- ローカル: `tsc --noEmit` green、Vitest **61** green、`vite build` 成功。UI/配線変更でロジックのしきい値意味は既存テストで担保。
- 未確認（実機・調整）: どの minObs 値で面がクリーンになり FPS が戻るか、別角度でのノイズ増が抑えられるか。→ `docs/PROGRESS.md` の Phase 6.3 手順で依頼。最適値が出たら既定に採用。

1. **カービングは「ボクセル→深度画像 逆投影」で判定**（レイマーチではなく）

## 2026-07-23 — Phase 6.1: スキャン範囲拡大＋近接での色精度向上（+ Phase 6 実機合格）

### Phase 6 実機合格

`build: 11:49Z` を Pixel 9a で確認。表示サイズスライダーで **2cm→16cm(×8)→8cm(×4) が再スキャンなしで即再構成**、`描画中` も 150,000→4,356→18,244 と変化、2cm へも復帰。→ **Phase 6 完了**。あわせてユーザ要望を受領: (a) もっと広いフィールドを取り込みたい、(b) 一度撮った所も近づくと精度が上がるとよい。

### 何を（Phase 6.1）

- **範囲拡大**: `GRID_CAP` 60 万→**200 万**、`RENDER_CAP` 15 万→**25 万**。実機で `破棄 100 万超` を観測しており、内部 2cm の取り込み量を実際に増やす。
- **距離重み付けの色**: `VoxelGrid.addPoint` に `weight`（既定 1）を追加。セルは生の観測数 `count`（占有しきい値用）に加え `wSum`（重み和）を持ち、色は **`rSum/wSum` の重み付き平均**。`main` は各観測の**カメラからの距離**で重みを決める（`1/max(d,0.3)`＝近いほど重い）。近い＝高密度・低ブレ・正確なので、再訪・接近で色が実物へ寄る。既定 `weight=1` では従来の単純平均に一致（既存テスト不変）。
- **coarse 再構成のタイミング変更**: k>1 の連続 0.4 秒スロットル全再構築を廃止。**スライダー変更時と一時停止トグル時のみ** `rebuildDownsampled`。ループでは k>1 のとき `grid.clearDirty()` で描画用 dirty を毎フレーム破棄（肥大化防止）。
- テスト: 重み付き色 2 件（重み比 3:1 の混色 / 既定重みで単純平均）、計 **54**。

### 主要な判断とその理由

1. **範囲は「内部上限を上げる」で対応（表示の粗さ変更＝Phase 6 では取り込み量は増えない）**
   - 理由: このアプリの目的は「ある程度広いフィールドのマップ化」。表示を粗くしても内部 2cm の取り込み総量は不変なので、`GRID_CAP` を上げるのが直接の解。差分ライブ描画は grid サイズに依存しないため、2cm スキャン自体は 200 万でも 60fps 級を維持できる想定。メモリは ~200MB 前後で 8GB 機なら許容見込み（実機で OOM 確認）。
2. **色は距離重み付け（幾何は 2cm 固定）**
   - 理由: 「近づくと精度が上がる」を、要件の 2cm 固定を保ったまま実現する最小の方法。遠い（ブレた）観測より近い（鮮明な）観測を色に強く効かせる。幾何の細分化は要件外なので触らない。近接では未取得セルが埋まる（カバレッジ向上）ことでも“良くなる”体感が出る。
   - 制約: 2cm ライブ描画は Phase 4 最適化で「最初に確定した色」で固定のため、色の改善は俯瞰プレビュー/coarse/エクスポート側に出る（ライブ 2cm 色更新は再アップロード増になるため今は見送り）。
3. **coarse はスライダー/一時停止でのみ再構成**

## 2026-07-23 — Phase 6: 表示ボクセルサイズ可変（整数倍ダウンサンプル）（+ Phase 5.1 実機合格）

### Phase 5.1 実機合格

`build: 11:25Z` を Pixel 9a で確認。差分更新化で **FPS 10 → 60 に回復**（描画 15 万・グリッド 60 万の上限でも 60fps、所感「かなり快適」）。俯瞰プレビュー等も正常 → **Phase 5 完了**。

### 何を（Phase 6）

- `src/voxel/grid.ts`: `forEachDownsampled(factor, minObs, cb)` を追加。確定 2cm セルを整数 `factor` 倍のセルへ集約（`Math.floor(idx/factor)`）。色は生の sum を合算してから割る＝**全観測の真の平均**（観測数で自然加重）。`factor=1` は確定セルと完全一致（`forEachConfidentPoint` に委譲）。表示・エクスポートを再スキャンなしに粗くする土台。あわせて `markAllDirty()`（2cm 表示へ戻す際の再シード用）。
- `src/render/voxelRenderer.ts`: ジオメトリを**単位立方体**にし、実サイズは**インスタンスごとの scale** で与える方式に変更（1 メッシュで 2 経路を共有）。`applyUpdates`（factor=1・差分ライブ、scale=2cm×0.55）はそのまま、`rebuildDownsampled(grid, factor, minObs)`（粗い全再構築、scale=factor×2cm×0.9）を追加。粗経路はスライダー変更時とスキャン中スロットルで呼ぶ。
- `src/main.ts`: HUD に**表示サイズスライダー**（1〜8＝2〜16cm）。ドラッグ中はラベルのみ更新、`change`（離した時）に再構成＝「即再構成」。k=1 は毎フレーム `applyUpdates`（ライブ）、k>1 はスライダー変更で即 `rebuildDownsampled`＋スキャン中は `DOWNSAMPLE_MS`(0.4s) ごとに再構成。2cm へ戻す時は `reset()`＋`markAllDirty()` で差分ライブに復帰。統計に「表示サイズ」行、描画数は `voxels.drawn` を表示（k>1 で正確）。
- `src/style.css`: `.size-row` / `.size-slider`（`accent-color`）等。
- テスト: `forEachDownsampled` に 3 件（factor=1 一致 / 2×2×2 集約と平均色 / 別ブロック分離）、計 **52**。

### 主要な判断とその理由

1. **内部は 2cm 固定、スライダーは「表示（＝エクスポート粒度）」のダウンサンプル**（要件どおり表示と内部を分離）
   - 理由: 過去データを無効化しないため蓄積は最細のまま。表示/出力は整数倍で間引く。`factor=1` が確定セルと一致するよう設計し、2 経路（ライブ差分 / 粗再構築）を素直に切り替えられる。
2. **単位立方体＋インスタンス scale**
   - 理由: 1 つの InstancedMesh で任意サイズを描けるようにするため。ジオメトリ再生成なしに factor を変えられる。
3. **再構成はスライダーの `change`（離した時）で**（`input` 連続発火では毎回 O(グリッド) 集約が走る）
   - 理由: ドラッグ中に全集約を繰り返すとモバイルで固まる。ドラッグ中は目標サイズのラベルだけ更新し、離した瞬間に一括再構成すれば「即再構成」を満たしつつ滑らか。
4. **俯瞰プレビューは 2cm 固定**
   - 理由: プレビューは「どこを撮ったか」の被覆マップで、キャンバス画素へ既に集約されるためサイズ差の意味が薄い。ここを可変にすると factor>1 で全集約スイープが毎ティック走り Phase 5.1 の FPS 改善を打ち消す。表示サイズの効果は 3D 側で見えるので割り切った。
5. **k>1 のスキャン中は 0.4 秒ごとに再構成**
   - 理由: k>1 は主に「スキャン後に粗さを確認」する用途。スキャン継続時も緩く追従させつつ、毎フレーム集約は避ける。

### 検証

- ローカル: `tsc --noEmit` green、Vitest **52** green、`vite build` 成功。
- 未確認（実機）: スライダーで 3D 表示が再スキャンなしに即再構成されるか、粗さ・描画数が変わるか、2cm へ戻せるか、スキャン中の切替。→ `docs/PROGRESS.md` の Phase 6 手順で依頼。

## 2026-07-23 — Phase 5.1: 俯瞰プレビューの差分更新化（FPS 回復）

### 実機で見つけた問題

Phase 5（`build: 10:24Z`）を Pixel 9a で確認。上下分割・俯瞰プレビューの成長・向き・スケールバーは良好（レイアウトの完了条件は満たす）。**しかし `FPS` が 74（Phase 4）→ 10 に低下**。原因は俯瞰プレビューが毎ティック（~7fps）でグリッド全 60 万セルを **2 回全走査**（bbox 用 + 描画用）していたため。モバイル CPU では 1 秒あたり 800 万回超の Map 走査になり、メインスレッドを飽和させ AR の描画/追従までカクついていた。

### 何を

- `src/voxel/grid.ts`: プレビュー用の**第 2 dirty セット** `dirtyPreview`（`drainDirtyPreview`）と、`addPoint` で O(1) 更新する**整数セル AABB**（`getBounds()`）を追加。レンダラ用 `dirty` と独立に消費できるので、レンダラ（毎フレーム）とプレビュー（~7fps）が互いに干渉しない。`clear()` は両 dirty と AABB をリセット。
- `src/render/overheadPreview.ts`: `render`（毎回全再描画）を `update`（差分）へ。永続 ImageData + 高さバッファを保持し、毎ティックは **`drainDirtyPreview` で得た新規確定ボクセルだけ**を追記描画（O(新規)）。**全走査（rebuild）は「初回データ出現時」と「成長で既存フィット外にボクセルが出た時」だけ**。再フィットには余白（8% / 最小 0.25m）を持たせ、通常の成長では再フィットが起きないようにした（Phase 4 と同じ「基本は追記、稀に全再構築」パターン）。`getBounds()` から bbox を取るので bbox 用の全走査も不要に。
- `src/main.ts`: `overhead.render` → `overhead.update`、クリアは `overhead.reset()`。
- テスト: grid の `getBounds`／`drainDirtyPreview` 独立性に 3 件追加、計 **49**。

### なぜ / 判断

1. **プレビューも「追記のみ、稀に全描画」に**（Phase 4 と同型）
   - 理由: ボクセルは基本増える一方。全走査は本質的に O(グリッド) で、60 万規模ではモバイルで破綻する。差分なら O(新規)。GPU ではなく CPU の Map 走査がボトルネックだったため、走査自体を無くすのが正攻法。
2. **グリッドに第 2 dirty セットを持たせる**（main/renderer の dirty 経路は不変）
   - 理由: レンダラは既に `drainDirty` を毎フレーム消費している。プレビューは別カデンス（~7fps）で消費するため、単一 dirty を共有すると取りこぼす。独立セットにすれば各消費者が自分のタイミングで全変更を受け取れる。実装も局所的で既存経路を壊さない。
3. **再フィットに余白（ヒステリシス）**
   - 理由: 余白なしだと端に 1 セル増えるたびに全再描画（rebuild）が誘発され差分化の意味が薄れる。余白を持たせれば通常の成長は現フィット内に収まり、rebuild は稀になる。

### 検証

- ローカル: `tsc --noEmit` green、Vitest **49** green、`vite build` 成功。
- 未確認（実機）: FPS が Phase 4 相当（30 以上・できれば 60 前後）に回復するか、差分化でプレビュー表示が壊れていないか。→ `docs/PROGRESS.md` の Phase 5.1 手順で依頼。

2. **無割り当てのグリッド走査 API を追加**

## 2026-07-23 — Phase 4: 描画最適化（差分追記 + FPS メータ）（+ Phase 3 実機合格）

### Phase 3b 実機合格（R7 確定）

カメラ実色 readback が実機で動作。ボクセルが**実物の色**で着色され、サムネイルにカメラ縮小画像が表示（readback 成功）。色の向きは **X:正 / Y:反転**（`camFlipX=false` / `camFlipY=true`）で実物と整合することをユーザがスクショで確認 → **R7 合格**。これで Phase 3（深度→ワールド→2cm ボクセル→実色）は幾何(R6)・色(R7)ともに実機確認済みで**完了**。

### 何を（Phase 4）

- `src/voxel/grid.ts`: 変更セル追跡を追加。`addPoint` が触れたキーを `dirty: Set<number>` に記録。`drainDirty(cb)` で「前回以降に変化したキーだけ」を走査してクリア（無割り当て）。`readVoxel(key, out)` で 1 セルのワールド中心+平均色+観測数を `out` に詰めて返す（`forEach` の全走査を使わず 1 セルだけ読む経路）。`clear()` は dirty も消す。
- `src/render/voxelRenderer.ts`: 毎フレーム全再構築を廃止し、**追記専用**に書き換え。`applyUpdates(grid, minObs)` が dirty セルだけを見て、新たに閾値到達した未描画セルを InstancedMesh 末尾に追記。`keyToInstance` で二重追加を防止。追記した連続範囲のみ `instanceMatrix.addUpdateRange(start*16, added*16)` / `instanceColor.addUpdateRange(start*3, added*3)` で部分アップロードし、`mesh.count` を伸ばす。`reset()` でクリア（クリアボタン用）。
- `src/main.ts`: ループを差分駆動に。毎フレーム `voxels.applyUpdates(grid, MIN_OBS)`（O(変化数)）。`REBUILD_MS`(全再構築間引き) を廃し、`STATS_MS`(250ms) の統計間引きへ。`frameCount` を数え `fps = frameCount*1000/経過` を算出、HUD 一行目に `FPS` を表示。「クリア」は `grid.clear()` + `voxels.reset()`。
- `test/grid.test.ts`: dirty 追跡と `readVoxel` に 4 件追加（drainDirty は各セル 1 回→クリア / readVoxel の中心・平均色・観測数 / 不在キー→false / clear で dirty 空）。計 **36** 件。

### 主要な判断とその理由

1. **全再構築 → dirty 差分の追記専用に**
   - 理由: 旧実装は `forEach` で毎回グリッド全セルを走査し InstancedMesh を作り直していた（O(グリッド全体)/更新）。10 万規模では毎回 10 万走査で 30fps を割る。ボクセルは基本「増える一方」なので、変化セルだけ追記すれば更新コストは O(変化数) に落ちる。GPU 転送も追記分の連続範囲だけに絞れる（`addUpdateRange`）。
2. **既存インスタンスは「最初に閾値到達した時の色」で固定**
   - 理由: 追記専用にすると既存ボクセルの色は更新されない。だが色の**真の移動平均は grid 側が保持**し続けるので、エクスポート（Phase 7）は正しい平均色を出せる。表示は速度優先で固定色にし、正確さは内部表現に委ねる（表示と内部の分離という設計方針に一致）。
3. **色の再描画はしない（差分は追記のみ）**
   - 理由: 「色を後から更新」まで差分に含めると dirty セルごとに `setColorAt` の再アップロードが要り、動く物体で発火し続ける。MVP の完了条件は「30fps 維持」なので、まず追記のみで実現。色更新の増分は必要になった段階で検討。

- `src/xr/cameraColor.ts`: `CameraColorReader`。`XRWebGLBinding.getCameraImage(view.camera)` の WebGLTexture を FBO に attach → `blitFramebuffer` で 96x214 に縮小 → `readPixels` で CPU バッファ化（WebGL2）。`sample(u,v)` で正規化ビュー座標から色を引く。全操作を try/catch で保護し、失敗時は `failed` を立てて高さ色にフォールバック（AR 表示は絶対に壊さない）。`flipX/flipY` で色の向きを実機調整。
- `src/xr/reproject.ts`: `PointSink` を `(x,y,z,u,v)` に拡張（u,v = 正規化ビュー座標 = カメラ画像 UV）。
- `src/main.ts`: 毎フレーム描画後にカメラ readback（~10Hz スロットル）→ `renderer.resetState()` で three の状態を再同期。ボクセルはカメラ色（失敗/未取得時は高さ色）。操作に「🎨 色: カメラ/高さ」「🔃 色向き(4通り循環)」を追加、`↕上下反転` は flipY=ON 確定のため撤去。HUD にカメラ縮小サムネイル（readback 診断）+ 色状態。
- `vite.config.ts` + UI: `__BUILD_ID__`（ビルド時刻）を define し、トップページと HUD に `build:` 表示。キャッシュで古い版を見た時に一目で分かる。

### 主要な判断とその理由

1. **色は CPU readback（FBO+blit+readPixels）で取得**
   - 理由: 色はボクセルごとに移動平均で蓄積・エクスポートするため CPU 値が要る。`getCameraImage` は GPU テクスチャのみなので downscale して readback。full 855x1920 は重いので 96x214 に blit してから読む（GPU stall 低減、~10Hz）。
2. **徹底したフォールバックと診断**
   - 理由: readback はブラウザ/端末依存で最も壊れやすい。失敗しても高さ色で動作継続し、AR 表示を壊さない。サムネイル+色状態+色向きトグルで、実機だけで原因切り分け・向き調整ができるようにした（Web 検索はレート制限中のため、確定 API=getCameraImage + 標準 WebGL2 の範囲で実装し、不確実な向きは実機調整に委ねる）。
3. **ビルド表示の追加**
   - 理由: 実機テストで旧キャッシュ版を見てしまう事故が起きたため。`build:` 時刻で今の版が一目で分かる。恒久的な自動更新(SW)は複雑さ回避で見送り、`?v=` + 表示で対処。
4. **`↕上下反転(reproject flipY)` トグルを撤去**
   - 理由: R6 で flipY=ON が正しいと実機確認できたため、`flipY: true` に固定してボタン枠を色操作へ。

### 検証

- ローカル: `tsc` green、Vitest **32** green、`vite build`（`__BUILD_ID__` 置換を確認）。
- 未確認（実機）: R7 色（実物色になるか・色の向き・サムネイル・readback 可否）。→ `docs/PROGRESS.md` の Phase 3b 手順で依頼。

## 2026-07-22 — Phase 0: 事前調査

### 何を

- `docs/` を作成し、`RESEARCH.md` / `ENVIRONMENT.md` / `PROGRESS.md` / `HISTORY.md` を追加。
- Section 4 の 7 調査項目 + カメラ色取得（camera-access）を一次情報で調査。

### 主要な判断とその理由

1. **深度は `cpu-optimized` + `luminance-alpha` を第一候補**
   - 理由: ボクセル化は CPU で行うため CPU パスが自然。`luminance-alpha` は唯一サポート保証されるフォーマット。値は `raw * rawValueToMeters` で扱えばフォーマット非依存にできる。
   - リスク対策: 端末が `gpu-optimized` しか許さない場合の GPU readback 経路を設計に含める（実機 R2 で確認）。
2. **深度はカメラ主軸の垂直距離（eye-space Z）と確定**
   - 理由: ARCore 公式 + depth-sensing 原案 explainer が「レイ長ではない」と明記。逆投影は「レイ方向を垂直 Z でスケール」で実装する。
3. **色取得には `camera-access` が必須と判明（要件と base API の差分）**
   - 理由: `immersive-ar` 単体ではカメラ画素にアクセスできない。`getCameraImage()` は GPU テクスチャのみ。CPU 蓄積で色を使うには 1 フレーム 1 回の低解像度 readback が要る。→ Phase 3 のスコープに影響するため要判断事項として明示。
4. **表示は InstancedMesh、GLB 出力は greedy meshing 済みマージメッシュ + 頂点カラー、と役割分離**
   - 理由: InstancedMesh の instanceColor は glTF に素直に運べない。表示速度（Instanced）と出力互換（マージ + 頂点カラー）を分ける方が両立する。
5. **セッションは自前で `requestSession` して `renderer.xr.setSession()` に渡す**
   - 理由: three.js の `ARButton` は `depthSensing` 設定を注入しないため、`depthSensing`/`camera-access` を確実に含めるには自前構築が必要。
6. **three.js は r185 系で固定予定**
   - 理由: 2026-07 時点の最新安定（`three@0.185.x`）。

### 未確定 / 持ち越し

- 逆投影の y 規約と実寸スケールは実機キャリブレーション（R6）で確定。
- `.vox` 複数モデルのワールド配置（拡張チャンク）は MVP スコープ外候補。
